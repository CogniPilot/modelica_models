Native / Modelica estimator fidelity audit

The flight benchmark currently compares generated Modelica CogniPilot ESKF
(fusion horizon and state retrodiction) against native PX4 EKF2 and native
ArduPilot EKF3. It does not use the partial PX4 or ArduPilot Modelica ports as
flight estimators. The requested five-implementation flight comparison is not
yet qualified.

Native PX4 EKF2            f1c0a1f794ed        existing native replay  GPS/denied/loss-return

* Exactness applies to the supplied independent kernel cases, with the
  corrected external native-reference vector adapter described below.

Byte identity is checked on numerical output bit patterns under a declared
precision, toolchain, upstream revision, and common input. Generated source
text and different compilers need not be byte identical. A tolerance pass is
not an exact-match pass; an exact-match pass on implemented kernels does not
establish full-flight estimator parity.

ArduPilot strict differential result

A fresh Rumoca 0.10.2 export was compared to the external port's C++ oracle
using actual method bodies extracted from pinned ArduPilot Git objects. Both
run with float32. The facade provides storage/vector adapters and excludes
unsupported lifecycle paths; this is not a full Replay executable comparison.

160 independent cases: 80 combined predictions, 80 GPS horizontal-position
gate/corrections. Every case compares 24 nominal states, all 576 covariance
entries, the clipping counter, and both fusion decisions. GPS cases additionally
compare the gate ratio. The same fixture array supplies both implementations;
all 656 float32 input values per case are retained in an input trace.

Original external reference:
  96,560 compared components; 25 differing bit patterns.
  Seven nominal-state components and 18 covariance entries differed.
  All clipping counters, fusion decisions and gate ratios matched exactly.
  Maximum absolute error: 1.4901161193847656e-8.
  Maximum scaled error: 1.2537459421258837e-8.
  Maximum ULP distance: 512, on a small covariance entry near 2.3e-8.
  Exact checker exit status: 1 (failure), despite passing numerical tolerances.

Root cause: tests/native_facade.hpp implements Vec3 scalar division as a
reciprocal followed by component multiplication. Pinned upstream vector3.h
and vector3.cpp divide each component directly, including operator /= used
by quaternion axis-angle conversion. These forms differ in float32 rounding.

Corrected external reference:
  Change only the Vec3 scalar division adapter to componentwise division.
  All 13 Modelica files remain byte identical to the original external port.
  Fixture input hashes remain identical between both runs.
  96,560 / 96,560 components match bit for bit; zero numerical/ULP differences.
  Exact checker exit status: 0.
  A separate 480-case OpenModelica/native-double regression passes; its maximum
  scaled error is 5.896831196761716e-9. This double regression uses tolerances,
  and does not claim double-precision bitwise equality.

The correction is validated in an owned, separately licensed temporary copy:
/tmp/modelica-port-parity/ardupilot-ekf3-modelica/tests/native_facade.hpp
The canonical external repository is unchanged because it is read-only in this
session. No ArduPilot/PX4 filter algorithm or Modelica transcription was added
to this repository. The original and corrected runs are retained separately.

Default ArduPilot SITL uses HAL_WITH_EKF_DOUBLE=1. The exact kernel result uses
an explicit float32 oracle to match Rumoca's generated C. It does not establish
byte identity with the existing double-precision SITL flight replay binary.

PX4 result and open port gaps

The existing PX4 Modelica DifferentialStep exports successfully with released
Rumoca 0.10.2. Its declared upstream revision is bd62df5e3ac3f3f4a07da4518062a922492adb6c;
the flight benchmark uses f1c0a1f794edf8e5e974b6ed96df3f95eda0df39. A successful
export does not validate its arithmetic. Exact kernel parity remains unproven
until the port and oracle target the same upstream revision and precision.

The PX4 port also explicitly approximates position propagation in a flat local
frame, whereas native prediction maintains geodetic position. That approximation
must be examined for a bitwise whole-state contract; small numerical error is
not a sufficient justification to call it exact.

Both partial ports lack complete optical-flow/terrain/range and magnetic
fusion, sensor buffering, initialization, output prediction, height-source
orchestration, and GPS quality/reset/source-switching behavior. Their existing
state dimensions and process models are retained as upstream conventions;
neither can stand in for a native GPS-denied or GPS loss/return flight filter.
An external call into the native core would not constitute an independent
Modelica implementation of these missing paths.

Common-data / common-noise performance comparison requirements

All candidates must receive the same frozen timestamped physical samples and
availability trace, with unit/frame/exposure conversions verified after actual
serialization. The existing explicit-exposure study verifies these delivery
conversions but still has unequal effective measurement noise, bias drift,
priors and native source policies. Its rankings are configured-stack results,
not the requested fully matched-noise comparison.

Compare common physical noise densities and actual effective Q/R, not matching
parameter names or displayed numbers. In the pinned sources, optical-flow
noise is floored at 0.05 rad/s and magnetic noise at 0.01 Gauss. Native GPS noise
uses reported accuracy and floors. ArduPilot also adds angular-rate-dependent
magnetic variance. Its active terrain-range path consumes the range-noise
parameter as a variance, while the height path squares it. A matching profile
must account for the path actually active in the replay; do not silently claim
equal noise from equal parameter values.

Required metrics for each GPS, denied and loss/return window:
  RMS position (horizontal/vertical), velocity, attitude and heading error,
  including transient recovery and failures rather than dropping bad runs.
  NEES from full covariance at the same fusion epoch as state and truth, with
  explicit coordinate/unit transformations into shared navigation error states.
  NIS from raw innovations and innovation covariance at actual measurement
  attempts, including accepted and rejected observations and their effective R.
  Fusion acceptance/reset counts, runtime and memory under the same toolchain.

Native quaternion/tangent dimensions differ. PX4's derivation uses a world-frame
left attitude error, while the ESKF diagnostic uses a body-frame right error.
ArduPilot biases are stored as IMU increments per dtEkfAvg, not physical rates.
These covariances require transformation before common navigation NEES is
meaningful. Published output-predictor states cannot be paired with delayed P.
Native ArduPilot's standard covariance logs retain only diagonals; standard
innovation logs are quantized and lack full S. They cannot supply exact joint
NEES/NIS. Sequential scalar conditional NIS must be distinguished from a joint
measurement statistic. Correlated flight samples are descriptive, not independent
Monte Carlo draws for confidence-interval testing.

Full native covariance / per-attempt innovation instrumentation, runtime
effective-noise verification, PX4 revision alignment, and complete port paths
remain required before publishing the requested equivalent-filter comparison.
No universal superiority or complete Modelica/native parity is claimed here.

Validation and evidence

28 Python comparison tests pass. Exact-trace negative controls reject a one-ULP
mutation, signed-zero differences, missing/reordered/duplicate records, precision
incompatibility, malformed/nonfinite values, and differing input/revision
declarations. The original facade's 25 mismatches remain an integration negative
control. Ruff and Git whitespace checks pass. No complete firmware CI rerun,
commit, force push or flight qualification was performed for this audit.
