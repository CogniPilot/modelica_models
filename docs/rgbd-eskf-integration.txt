RGB-D, GPS and ESKF integration and matched coupling experiment
8 October 2026

User requirements
-----------------
Keep ESKF Apache-2.0 and independently implemented. Use CogniPilot slam_web's
existing camera/SLAM work. Compare loose and tight coupling on the same data.
One navigation interface supplies planning and control. GPS must georeference
the map. Include GPS, GPS-denied, loss/return, and visual tracking loss/return.

Read-only source review
---------------------
slam_web revision 34b9d3a99510e11a6e054093e273f3f9ade055a0 was inspected.
It already has raw RGB-D feature acquisition, registration with a relative
covariance, keyframe/reference retention, Schmidt relative-pose correction,
measured graph edges, graph correction and persistent map processing.
No source or running process in that checkout was changed for this review.

src/world-navigation.ts NavigationHandoff fits yaw/translation from paired
GPS/SLAM motion, then selects GPS position when available or aligned SLAM
position otherwise. It clears alignment after detected frame/loop changes.
Its own contract calls this a navigation display handoff, not tightly coupled
GNSS/VIO fusion. Do not reuse that display switch as the production estimator.
The authored D435 full-SLAM interface has camera and IMU inputs but no raw GPS
input. Existing component/native reference receipts do not establish a complete
source-issued browser SLAM runtime; those qualification limits remain relevant.

The current modelica_models ESKF has raw GPS, magnetic, pressure and nadir-flow
aiding, but not a general RGB-D visual aiding contract. RDD2's estimator branch
publishes estimator.estimate through avionics.navigation. Its separate truth
branch is for simulation diagnosis, not a real navigation source.

Ownership before frames
-----------------------
Both coupling alternatives use ONE navigation session that owns IMU state,
biases, covariance, visual reference uncertainty, accepted corrections and
GPS/world registration. The camera front end produces measurements and map
associations; it does not publish a competing authoritative vehicle pose.
The mapper consumes the session's poses and retains keyframe/map identities.
Loop proposals go through the same session's correction/commit policy.

A fixed local ENU world origin gives GPS an explicit datum. A visual map may
retain a convenient local frame; its world alignment is an uncertain part of
the navigation problem, not another independent filter estimate. A globally
referenced map can instead use that ENU frame directly. Neither representation
creates additional information. Choose one representation for the first test.

For a retained metric, gravity-aligned visual map, GPS antenna position obeys
  z_GPS = R_world_map p_map_body + t_world_map + R_world_body lever_body_antenna + n.
GPS constrains this model at its acquisition epoch. A single position fix does
not determine map yaw. Heading information or an adequate motion baseline is
needed. Depth supplies metric scale under the assumed calibrated depth model.
Without GPS or a prior georeferenced map, absolute translation remains a gauge.

Local control publication and global map publication are two views of that
single session, with explicit epochs, covariance and frame revisions. The
current-time output predictor serves control; historical fusion state is not
silently substituted. Global corrections/loop closures require an atomic update
of map transforms, pose views, references and world-referenced targets. A smooth
local publication is a separate output contract, not a reason to discard global
corrections or claim a delayed covariance belongs to the predicted present pose.

Never use a GPS-corrected pose as independent map evidence and then feed the
optimized map pose back as another independent measurement. Retain the needed
correlations or use an explicitly conservative bound for unknown correlation.
The current slam_web Schmidt and graph-correction components already address
parts of this issue; they should be reviewed and reused rather than bypassed.

Coupling alternatives
---------------------
Loose: the RGB-D front end estimates a relative/odometry pose and its complete
6x6 covariance, including translation/rotation cross terms. Fuse it through
the common navigation owner. IMU-aided external VIO is a distinct case with
shared process information and cannot be assumed independent. Correlation
with retained keyframes and reused images must be modeled or conservatively
bounded. Zeroing those cross terms is not a fair loose baseline.

Intermediate: retained-reference relative-pose fusion uses the measured 6D
relative pose and current/reference cross-covariance, as in the existing
Schmidt work. This is not labeled raw-feature tight coupling.

Tight: the same selected image/depth observations directly produce camera
residuals against retained poses/landmarks. Retain or correctly eliminate the
nuisance states and their correlations. Use the same raw measurements once;
do not also fuse the front end's pose from those same measurements.
Feature selection, calibration and timing are shared with the loose baseline.

Coordinate compatibility is a required first gate
------------------------------------------------
slam_web's inertial tangent is
  [dp_world, dv_world, dtheta_body, dba_body, dbg_body].
This repository's ordinary right-injected ESKF tangent is
  [dp_body, dv_body, dtheta_body, dbg_body, dba_body].
At first order, the mapping rotates position/velocity errors by R_world_body
and swaps the two bias blocks. Covariance, reference cross-covariance and
observation Jacobians must transform with it. The nominal injection and reset
maps also differ: this ESKF uses the full SE_2(3) exponential, while the existing
visual correction uses additive world translation and SO(3) injection.
A first-order covariance conversion alone does not make their finite updates
interchangeable. Derive the camera residual and reset in the chosen ESKF
coordinates and check independent finite differences, including lever arms.
Experimental SemiDirectBias coordinates need a separate derivation.

Matched experiment and completion evidence
-----------------------------------------
Use immutable RGB/depth, IMU and GPS captures with acquisition timestamps,
clock-domain conversion, camera/IMU extrinsics, camera calibration and depth
scale. Preserve held-IMU intervals and delayed image epochs. Apply equivalent
raw sensor noise assumptions, priors, sensor availability and time schedules.
Observation dimension and noise propagation legitimately differ between paths.

Test GPS flight, denied flight and GPS loss/return; add visual loss/recovery,
loop closure, delayed frames, weak texture/planar geometry, tilted motion,
nonzero biases and depth/calibration faults. Separate known development data
from frozen independent evaluation. Retain losses and refused observations.

Report physical position/velocity/attitude RMS and tail errors; state NEES at
the actual covariance epoch; NIS for the actual residual dimension/selection;
tracking/recovery time; global-frame consistency; CPU, peak memory and latency
on matched hardware. Pose-update and raw-feature NIS are not interchangeable.
Independent noise draws, not correlated flight ticks, define Monte Carlo count.
Maintain sensor/factor provenance and duplicate-fusion controls.

Tight coupling is not assumed to win. Under an appropriate common linear
Gaussian model, a pose compression that preserves sufficient information can
match the raw update. Differences must be traced to information loss, model
accuracy, nonlinear behavior, correlation treatment or computational limits.
Lean obligations include gauge preservation, consistent joint uncertainty,
measurement/reset bounds and delayed publication. No current proof certifies
this not-yet-integrated visual system or its superiority over native firmware.
